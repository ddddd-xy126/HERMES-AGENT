# AI 应用落地概念说明

> 当前日期：2026-06-22  
> 工作区：`AgentGroups`  
> 主题：Hermes Agent + Hermes Web UI + BrowserHarness 的项目解读与 AI 应用落地概念

## 1. 一句话结论

这是一个面向企业内部流程自动化的 AI Agent 落地工作区。

它把 Hermes Agent、飞书机器人、Web 管理控制台、BrowserHarness 浏览器自动化、定时任务和内部业务系统连接起来，让 AI 不只是聊天，而是能像一位数字同事一样进入内网系统查询、汇报和辅助操作。

可以把它理解为：

> 企业内网 AI 执行助理平台。

它的核心价值不是“回答问题”，而是“把自然语言转成可审计、可复用、可确认的业务动作”。

## 2. 这个项目是什么

当前工作区不是一个单一应用，而是由三个主要部分组成的 AI 执行系统。

### 2.1 `harmesAgent`：本地部署与运维工作区

`harmesAgent` 是“爱马仕 Lucky”的部署、配置和运维层。

它负责：

- 在 Windows + WSL2 Ubuntu 环境中部署 Hermes Agent。
- 管理 Hermes 的 gateway、dashboard、cron、memory、skill 等能力。
- 提供启动、重启、配置修复、Chrome 自愈、技能同步等脚本。
- 维护飞书机器人、BrowserHarness、51pm 内部系统等集成方案。
- 存放产品文档、使用教程、定时任务 prompt、人格与记忆规则。

换句话说，`harmesAgent` 是这个 AI 系统的“本地作战包”。

### 2.2 `hermes-web-ui`：Hermes Agent 的 Web 管理控制台

`hermes-web-ui` 是一个自托管的 Web UI，用于管理 Hermes Agent。

它提供：

- AI 聊天与多会话管理。
- 模型、Provider、凭证和配置管理。
- 用量分析、成本统计、日志查看。
- Cron 定时任务管理。
- 技能、记忆和文件浏览。
- Web 终端。
- 多 Profile、多网关管理。
- 多 Agent 群聊。
- 通过 BFF 代理 Hermes Gateway 的 API。

技术上，它由 Vue 3 前端和 Koa BFF 后端组成。

整体链路可以概括为：

```text
浏览器
  ↓
Hermes Web UI BFF，默认端口 8648
  ↓
Hermes Gateway，默认端口 8642
  ↓
Hermes Agent / LLM / Tools / Skills
```

在当前 `harmesAgent` 的脚本里，还使用 Hermes 自带 dashboard，端口为 `9119`。

### 2.3 `BrowserHarness`：真实浏览器自动化能力层

`BrowserHarness` 是一个基于 CDP 的浏览器控制工具。

它的目标是让 AI 能直接操作用户已经启动的 Chrome，而不是只能调用 API 或模拟文本流程。

它提供：

- 打开新标签页。
- 等待页面加载。
- 截图。
- 坐标点击。
- DOM 读取。
- JavaScript 执行。
- 下载、上传、滚动、处理 iframe、弹窗等。
- 针对具体网站沉淀 domain skill。

它的典型调用方式是：

```bash
browser-harness -c '
new_tab("https://example.com")
wait_for_load()
print(page_info())
'
```

在这个项目里，BrowserHarness 主要用于让 Hermes Agent 操作内部 Web 系统，例如 51pm。

## 3. 它有什么用

这个项目的目标，是把 AI 从“对话工具”升级成“能办事的工作流执行者”。

已经明确落地的业务场景是 51pm 内部项目管理系统。

### 3.1 已落地场景：51pm 任务查询与播报

用户可以在飞书里向机器人发送类似请求：

```text
本周组员任务
```

Agent 会执行以下动作：

1. 检查 automation Chrome 是否可用。
2. 如果 Chrome 没起来，自动拉起。
3. 复用已有 51pm 标签页，或打开新的 51pm 页面。
4. 进入正式或测试环境。
5. 根据部门、状态、日期范围筛选任务。
6. 分别读取“项目任务”和“非项目任务”两个 tab。
7. 合并任务清单。
8. 返回给飞书用户。

典型输出包括：

- 本周日期范围。
- Web 端开发组进行中任务总数。
- 项目任务列表。
- 非项目任务列表。
- 任务名称、指派人、剩余工时等字段。

### 3.2 定时任务场景

项目里已有每日任务播报 prompt。

例如每天 8:40 自动执行：

- 查询 51pm 正式环境。
- 获取本周 Web 端开发组进行中任务。
- 合并项目任务与非项目任务。
- 主动推送到飞书。

这让 AI 具备了“主动服务”的能力，而不只是被动问答。

### 3.3 写操作辅助场景

对于“完工”等写操作，系统通过 skill 约束了安全流程：

- 必须先列出任务并编号。
- 必须让用户明确选择要操作的编号。
- 必须区分项目任务 `P-xx` 和非项目任务 `N-xx`。
- 必须避免误点编辑、工时、删除按钮。
- 每次点击后必须刷新表格并重新定位下一条任务。
- 对于正式环境写入，要格外谨慎。

这说明这个系统不是简单的浏览器脚本，而是在向“可控的 AI 业务执行”演进。

### 3.4 可扩展场景

当前 51pm 是样板，未来同样模式可以扩展到：

- OA 审批。
- Jira 或禅道任务管理。
- 工时填报。
- 日报、周报生成。
- 飞书文档与知识库。
- PDF、PPT、图片和多媒体生成。
- GitHub / GitLab 研发协作。
- 内部报表查询。
- 采购、供应商、项目交付等系统。

只要能被浏览器访问，并且流程可复现，就可以通过 BrowserHarness + domain skill 沉淀成 AI 可执行能力。

## 4. 它是如何运转的

### 4.1 总体链路

整体运行链路如下：

```text
用户
  ↓
飞书 / Web UI / Cron
  ↓
Hermes Agent Gateway
  ↓
LLM 模型
  ↓
Memory / Skill / Tool 调度
  ↓
BrowserHarness CLI
  ↓
BrowserHarness Daemon
  ↓
CDP 连接 Windows automation Chrome
  ↓
内部 Web 系统，例如 51pm
  ↓
读取结果 / 执行动作 / 返回用户
```

### 4.2 飞书入口

飞书机器人是日常使用入口。

用户在飞书里 @ 爱马仕 Lucky，消息进入 Hermes Gateway。Gateway 把消息交给 Hermes Agent，Agent 根据系统配置、记忆、技能和用户输入决定如何处理。

如果只是普通问答，它会直接调用 LLM 回复。

如果涉及内部系统，例如“本周任务”“完工”“工时”“日报”，它会根据全局规则和 BrowserHarness skill 调用浏览器自动化能力。

### 4.3 Web UI 入口

Web UI 提供图形化管理入口。

它可以用来：

- 直接聊天。
- 查看会话历史。
- 查看 Agent 调用了哪些工具。
- 管理模型和 Provider。
- 管理配置和环境变量。
- 查看日志。
- 管理 Cron 任务。
- 浏览技能和记忆。
- 使用 Web 终端。

技术上，前端请求先进入 Koa BFF，再由 BFF 代理到 Hermes Gateway。

### 4.4 Cron 入口

Cron 让 Agent 可以定时执行任务。

例如：

```text
每天 08:40 查询 51pm 本周任务并推送飞书
```

Cron prompt 是自包含的，里面写清楚：

- 要查哪个环境。
- 要进入哪个页面。
- 要用哪个 skill。
- 要只读还是允许写入。
- 输出格式是什么。
- 是否允许追问后续动作。

当前 daily 任务明确要求只读，不主动追问“要不要完工”。

### 4.5 BrowserHarness 与 Chrome

BrowserHarness 不自己启动普通浏览器，而是连接一个独立的 automation Chrome。

在当前设计中：

- Chrome 跑在 Windows 侧。
- Hermes 和 BrowserHarness 跑在 WSL Ubuntu 侧。
- Chrome 开启 remote debugging 端口 `9333`。
- WSL 通过 `BU_CDP_URL` 访问 Windows 主机的 Chrome CDP 地址。
- BrowserHarness daemon 解析 `/json/version`，拿到 WebSocket URL。
- 后续所有页面控制通过 CDP 完成。

这样做的好处是：

- 保留 Windows 上的企业内网访问能力。
- 使用独立 Chrome profile，避免污染用户日常浏览器。
- 登录态可以持久保存。
- AI 可以看见真实页面，而不是只依赖接口。

### 4.6 技能系统如何工作

BrowserHarness 的技能分两类：

1. **interaction-skills**  
   通用浏览器交互能力，例如弹窗、下载、上传、iframe、滚动、截图等。

2. **domain-skills**  
   具体站点的业务知识，例如 51pm、amazon、arxiv、github、youtube 等。

对于 51pm，skill 里记录了很多生产经验：

- 正式环境和测试环境必须明确区分。
- 进入页面前要复用已有 tab，避免开一堆重复页面。
- 51pm 是 Vue + Element UI，筛选时优先直接操作 Vue data，而不是笨拙点击 DOM。
- 项目任务和非项目任务是两套数据，必须分别查询。
- Element UI 表格有固定列重复渲染，读取时要选主表体。
- 写操作必须经过用户确认。
- 完工按钮、编辑按钮、工时按钮、删除按钮必须严格区分。
- 不能缓存坐标连续点击，因为表格刷新会导致行错位。

这就是“AI 经验沉淀”的关键：

> 第一次踩过的坑，下一次不再让 Agent 重踩。

## 5. 关键组件职责

| 组件 | 职责 |
|---|---|
| Hermes Agent | 核心 Agent 框架，负责 LLM 调度、工具调用、技能、记忆、cron、gateway |
| Hermes Gateway | 接收飞书等平台消息，运行 Agent，返回响应 |
| Hermes Dashboard | Hermes 自带的 Web 控制台，当前脚本使用端口 `9119` |
| Hermes Web UI | 独立的现代化 Web 管理面板，默认端口 `8648` |
| Koa BFF | Web UI 后端，代理 Gateway API，管理会话、配置、日志、文件、终端等 |
| BrowserHarness CLI | 给 Agent 调用的浏览器自动化命令行入口 |
| BrowserHarness Daemon | 维持 CDP WebSocket 连接，执行浏览器控制请求 |
| automation Chrome | Windows 侧独立 profile 的真实 Chrome，访问内网业务系统 |
| domain-skills | 站点级业务经验库，记录 URL、流程、选择器、陷阱和安全约束 |
| Cron Prompt | 定时任务执行说明，让 Agent 定时主动工作 |
| USER.md / memory | 全局硬规则，例如 Chrome 自愈、51pm 任务前置规则等 |

## 6. 这个 AI 应用的落地概念

我建议把这个项目包装成一个明确的 AI 应用概念：

# 企业内网 AI 执行助理平台

它面向的不是泛聊天，而是企业内部高频、重复、跨系统、半结构化的工作。

用户通过自然语言发出指令，AI 根据企业知识、历史技能、浏览器自动化和安全规则，进入真实业务系统完成查询、汇总、提醒和受控操作。

它适合的定位是：

- 项目团队的任务助理。
- 交付团队的日报/周报助理。
- 研发团队的工时和排期助理。
- 内部系统的自然语言操作入口。
- 跨系统流程自动化 Agent。
- 企业低代码/无 API 场景下的 AI RPA。

## 7. 这个应用的特点

### 7.1 面向真实业务系统

它不是只在 demo 页面里工作，而是直接面向内部系统。

例如 51pm 是企业项目、任务、工时、排期管理系统，里面有正式环境、测试环境、企业微信 OAuth、Element UI 表格、分页、筛选、写操作等真实复杂度。

### 7.2 不依赖业务系统开放 API

很多企业内部系统没有稳定 API，或者 API 不开放给个人自动化使用。

BrowserHarness 通过真实浏览器和 CDP 操作页面，因此可以绕过“没有 API 就不能自动化”的限制。

这让它很适合传统企业、内网系统、遗留系统和第三方后台。

### 7.3 经验可以沉淀为 skill

每个站点的经验都可以写成 domain skill。

例如：

- 页面入口。
- 登录方式。
- 表单字段。
- DOM 结构。
- Vue data 位置。
- 稳定选择器。
- 表格读取方式。
- 写操作确认流程。
- 曾经发生过的事故和规避方法。

这让系统越用越懂企业流程。

### 7.4 支持人机协同确认

系统没有把写操作完全交给 AI 放飞。

对于完工、删除、提交、新增等动作，skill 明确要求：

- 先列出影响对象。
- 再让用户选择。
- 必要时逐条确认。
- 点击后重新读取状态。
- 最后截图或汇报结果。

这很适合企业内部场景，因为企业场景最怕“AI 很聪明但不受控”。

### 7.5 支持主动服务

Cron 能让 AI 主动执行任务。

例如：

- 每天早上推送本周任务。
- 每天下班前检查日报。
- 每周生成排期统计。
- 每月汇总项目风险。

这让 AI 从“问了才答”变成“到点就干”。

### 7.6 自托管，适合内网

系统运行在用户自己的 Windows + WSL 环境里。

数据、配置、skill、记忆、日志、Chrome 登录态都在本地或内网环境中。

这比完全云端的 Agent 更适合企业内网自动化。

### 7.7 具备可观测性

通过 Web UI 或 dashboard，可以看到：

- 会话记录。
- 工具调用过程。
- Token 用量。
- 日志。
- Cron 任务。
- 技能列表。
- 配置和 Provider。
- 网关状态。

这让系统更容易排错、展示和管理。

## 8. 当前项目的成熟度判断

从代码和文档看，它已经不是纯概念验证，而是一个“已跑通过具体业务场景的内部 AI Agent 系统”。

成熟的地方：

- 有完整部署文档。
- 有 Windows + WSL 的环境方案。
- 有飞书入口。
- 有 Web UI。
- 有 BrowserHarness 接入。
- 有 Chrome 自愈脚本。
- 有技能同步机制。
- 有 51pm 业务 skill。
- 有每日 Cron prompt。
- 有安全边界和事故复盘。

仍需注意的地方：

- 一些脚本中硬编码路径是 `/mnt/d/webDevFrontProject/AgentGroups/...`，而当前工作区路径是 `d:\project\AI-Agent\AgentGroups`。如果要在当前目录直接运行，需要统一修正路径。
- 正式环境写操作风险较高，需要继续加强确认、审计和回滚能力。
- 目前很多能力依赖本机 Chrome 登录态，换机器或换账号需要重新初始化。
- Browser 自动化对页面结构变化敏感，需要持续维护 domain skill。
- 如果要给团队多人使用，需要明确权限边界、飞书白名单、日志脱敏和密钥管理。

可以考虑以下产品化表达：

- 企业工作流 Agent 平台。

如果要面向同事介绍，可以说：

> 爱马仕 Lucky 是一个接入飞书和内部系统的 AI 助手。它可以帮团队查任务、看工时、生成播报、进入网页后台执行受控操作，并且会把常用流程沉淀成技能，越用越懂我们的工作方式。

如果要面向技术团队介绍，可以说：

> 这是一个基于 Hermes Agent 的自托管企业 Agent 运行环境，通过 BrowserHarness 连接真实 Chrome，以 domain skill 方式沉淀内网页面自动化经验，并通过飞书、Web UI 和 Cron 提供交互、管理与主动执行入口。

## 10. 推荐的下一步

如果要继续把它做成一个更完整的 AI 应用，建议优先推进：

1. **统一路径配置**  
   把脚本里的硬编码路径抽成配置，避免不同机器、不同目录下不可运行。

2. **沉淀更多业务 skill**  
   以 51pm 为模板，继续接入 OA、日报、工时、排期、审批等高频场景。

3. **建立写操作审计**  
   对所有写操作保存：用户请求、确认内容、执行对象、执行前后截图、时间戳。

4. **做一份团队使用手册**  
   面向非技术同事说明：能问什么、不能问什么、哪些操作需要确认、遇到问题找谁。

5. **做权限与白名单治理**  
   限定哪些飞书用户能触发正式环境操作，哪些用户只能只读查询。

6. **把 51pm 能力产品化**  
   可以先形成一个清晰 MVP：
   - 每日任务播报。
   - 本周任务查询。
   - 今日工时查询。
   - 周报生成。
   - 受控完工。

## 11. 最终概括

这个项目本质上是在做一件很有价值的事：

> 让 AI 从“会聊天”变成“能进入企业系统干活”。

它用 Hermes Agent 做大脑，用飞书和 Web UI 做入口，用 BrowserHarness 做手脚，用 domain skill 做经验沉淀，用 Cron 做主动服务，用安全确认机制控制风险。

这就是一个 AI 应用从 demo 走向落地的关键形态：

- 有真实用户入口。
- 有真实业务系统。
- 有真实流程。
- 有可复用技能。
- 有主动触发能力。
- 有安全边界。
- 有运维和可观测性。

因此，它最适合作为“企业内部 AI Agent / AI RPA / 数字助理”的落地样板继续演进。
